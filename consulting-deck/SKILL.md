# consulting-deck

コンサル風の戦略・分析資料を、毎回同じレイアウトで作るためのスキル。
**すべての座標・色・フォントサイズは `scripts/deck_lib.js` に固定されている。** スライドは必ずこのライブラリの関数で作り、座標やフォントを直接書かないこと。これにより、どの資料でもタイトル位置・本文エリア・出典欄・ページ番号が揃う。

## 全体の流れ

1. メモを読み、ストーリーを組み立てる（下記「メモの整理」）
2. 構成案（メッセージタイトルの一覧）を先にユーザーへ提示し、確認をとる
   - ユーザーが「任せる」「そのまま作って」と言っている場合は省略してよい
3. `examples/sample_deck.js` を作業ディレクトリ（例 `/home/claude/work/build_deck.js`）にコピーし、内容を差し替えて生成スクリプトを書く
   - コピー後、`require` のパスをこのスキルの `scripts/deck_lib.js` の絶対パスに書き換える（スキルの場所は `ls /mnt/skills/*/consulting-deck` で確認）
4. 実行して `.pptx` を出力し、QA（下記）を行う
5. `/mnt/user-data/outputs/` に置いて提示する

生成の前に `/mnt/skills/public/pptx/SKILL.md` のQA手順（validate.py、画像化）も参照すること。

## メモの整理（ピラミッド構造）

メモは箇条書きのままでも、順番がバラバラでもよい。以下の順で組み直す。

1. **資料全体の結論**を1文で決める（これがエグゼクティブサマリーの lead になる）
2. 結論を支える**根拠**を洗い出し、セクション（現状と課題／打ち手の検討／提言／実行計画など）に振り分ける
3. 各スライドの**メッセージタイトル**を「主語＋述語で言い切る1文」で書く。トピック名（「現状分析」「課題」）だけのタイトルは不可
4. 本編に入りきらない詳細データ・算出根拠・前提の細部は **Appendix** に回す

メモに**足りない要素**があれば、スライド作成前にユーザーへ指摘する。例：
- 結論を支える根拠データがない
- 提言に対する効果（数値）がない
- 誰がいつ何をするか（ネクストステップ）が書かれていない

数値がメモにない場合、**数字を創作しない**。「約〇億円（要試算）」のように仮置きであることを明示する。

## 必須構成

標準は本編10〜15枚（Appendixは枚数に含めない）。

| # | スライド | 関数 | 必須度 |
|---|---|---|---|
| 1 | 表紙 | `cover` | 必須 |
| 2 | エグゼクティブサマリー | `executiveSummary` | 必須 |
| 3 | アジェンダ | `agenda` | 任意 |
| 4 | 前提条件・スコープ | `scope` | 任意（仮定が多い場合は要点のみ本編、詳細はAppendix） |
| 5 | 現状と課題 | `flow` / `textVisual` | 任意 |
| 6 | 分析・検討 | `matrix2x2` / `comparison` / `textVisual` | 任意 |
| 7 | 提言 | `textVisual` / `columns` | 任意 |
| 8 | 期待効果・KPI | `kpi` | 任意 |
| 9 | ロードマップ | `roadmap` | 任意 |
| 10 | ネクストステップ | `nextSteps` | 必須 |
| 11 | Appendix | `divider` → 各レイアウト（section: "Appendix"） | 任意 |

### エグゼクティブサマリーのルール

- 要点の数は固定しない。内容に応じて決める
- 各要点は本編のセクションやメッセージタイトルと対応させる
- 最重要の結論は `lead` に置き、キーワードを `==強調==` でオレンジにする
- 1スライドに収まらない場合は、要点を統合するか詳細を本編に委ねる
- **サマリーは本編をすべて書いた後に最終化**し、本編と矛盾がないか確認する

### Appendixのルール

- 本編の後に `divider({ label: "Appendix" })` で中扉を入れる
- ページ番号は本編から通し（自動）。セクション表示は `"Appendix"`
- 本編の注記に「詳細はAppendix p.〇参照」と書き、対応を明示する

## レイアウト関数（詳細は references/layouts.md）

| 関数 | 用途 |
|---|---|
| `cover` | 表紙 |
| `executiveSummary` | 結論（lead）＋番号付き要点 |
| `agenda` | セクション一覧（`current` で該当セクションを強調） |
| `scope` / `columns` | 2〜4列の並列整理（前提条件・スコープなど） |
| `flow` | 現状→課題→施策の横並び（最後の列を強調） |
| `textVisual` | 左に要点・右にグラフ（文章と図のバランス型の基本形） |
| `matrix2x2` | 優先度・ポジショニング |
| `comparison` | 選択肢の比較表（推奨案の列を強調） |
| `kpi` | 期待効果・KPIのカード |
| `roadmap` | ガントチャート形式のスケジュール |
| `nextSteps` | アクション表＋ご判断いただきたい事項 |
| `text` | 箇条書きのみ（Appendix等） |
| `divider` | 中扉 |

すべてのコンテンツ系レイアウトで共通の引数：`title`（メッセージタイトル・必須）、`section`（セクション表示）、`source`（出典）、`note`（注記）、`takeaway`（下部の示唆ボックス・任意）。

**同じレイアウトを3枚以上連続させない。** 内容に合わせて flow / textVisual / matrix2x2 / comparison を使い分ける。

## デザインルール（ライブラリで固定済み・変更しない）

- **スライド**：16:9、白背景、フォントはメイリオ
- **文字サイズ**：表紙タイトル32pt／メッセージタイトル20pt太字／サマリーの結論18pt太字／本文16pt（箇条書き2階層目14pt）／図表ラベル11〜12pt／セクション表示10pt／出典・注記・ページ番号9pt。本文は11pt未満にしない。入らないときは文字を削るかスライドを分ける
- **罫線**：タイトルと本文を区切る上罫線（y1.55）と、本文と出典欄を区切る下罫線（y6.85）を全スライドに配置。色 #DEDEDE、太さ0.75pt、幅はコンテンツ幅（左右0.5インチ内側）。マスターに固定されているので個別に描かない
- **色**：本文 #2D2D2D、補足 #7D7D7D、罫線 #DEDEDE、強調 #D04A02（オレンジ）、グラフの2・3系列目 #EB8C00→#FFB600（注目箇所を指定しない場合のみ）、警告 #E0301E（限定使用）。企業ロゴやワードマークは入れない
- **強調の記法**（テキスト中で使う）
  - `**太字**` → 太字。個数の制限はないが、使いすぎに注意する
    - 目指す状態：**本文を読まなくても、太字だけを流し読みすれば各スライドの要点がわかる**。結論のキーワード、重要な数値、主語と述語の核になる語句を太字にする
    - 太字は必須ではない。短い箇条書きだけのスライドなど、太字がなくても要点が明らかな場合は使わなくてよい
    - 太字が本文の4割を超えると「要確認」に警告が出る。太字が多すぎると、どこが重要か逆にわからなくなるため
  - `==強調==` → オレンジ太字。1スライド2か所まで
  - 太字＋オレンジ＋大きい文字の重ねがけは、そのスライドの最重要1か所だけ
  - 文章まるごとの太字、下線、斜体は使わない
- **グラフ**（`chart` / `textVisual` の visual.chart で作る。ライブラリで自動適用）
  - **凡例は必ずグラフの中かすぐそばに置く**。円グラフはスライスの外側に「項目名＋%」、ドーナツはセグメント上に「項目名＋%」を直接表示し、離れた位置の凡例は使わない。複数系列の棒・折れ線はグラフ上部に凡例を置く。1系列の棒グラフは項目名を軸ラベルで、系列名と単位を `visualTitle`（例「部門別の受注率（%）」）で示す
  - **注目してほしい箇所だけオレンジにし、それ以外はグレーにする**。`highlight` に項目（1系列の棒・円・ドーナツ）または系列（複数系列の棒・折れ線）の index を指定する。グラフを使うときは原則すべてで指定し、注目箇所はメッセージタイトルの主張と一致させる
  - 未指定のときは「要確認」に警告が出る。全項目を同じ重みで見せたい場合のみ、理由を持って未指定にする
- **近接のルール（関係するものは近く、関係しないものは離す）**
  - 見る人は「近くにあるもの＝ひとまとまり」と受け取る。余白の大小で、どこからどこまでが1つのまとまりかを伝える
  - **関係する要素は近づける（0.1インチ）**：見出しとその本文、グラフとその見出し、表とその補足、KPIの数値とラベル、親項目とその子項目
  - **別のまとまりは離す（0.4インチ）**：列と列、カードとカード、サマリーの結論と要点一覧、本文エリアと示唆ボックス
  - 箇条書きは、親子の間隔（3pt）を項目同士の間隔（8pt）より狭くし、どの子項目がどの親に属するかが一目でわかるようにする
  - 見出しと本文を左右に並べる場合（サマリーの要点など）も、見出しの横に大きな空白をつくらない
  - 間隔の値はライブラリの `G.NEAR` と `G.GAP` で固定済み。`textVisual` の描画関数などで自由に配置するときも、この2つの値だけを使い、中途半端な間隔をつくらない
- **箇条書き**：2階層まで（`{ text, sub: [...] }`）
- **ステータス表示**：`new Deck({ status: "Draft" })` で全スライド（表紙含む）の右上に、ミドルグレー（#7D7D7D）の枠線0.75pt＋同色の太字11ptで表示。オレンジは本文の強調と紛れるため使わない。指定がなければ非表示

## 作成ルール

### 縦読み・横読みチェック（必須）
`save()` 実行時に「縦読み（メッセージタイトルの流れ）」が出力される。
- **縦読み**：タイトルだけを順に読んで、結論→根拠→提言→次の一手の話が通るか確認する
- **横読み**：各スライドのタイトルと本文・図の中身が一致しているか確認する
問題があればタイトルか中身を直して再生成する。チェック結果（修正した点）はユーザーへの報告に一言添える。

### 数値・表記の統一（必須）
資料全体で以下を揃える。
- 金額の単位（億円／百万円のどちらかに統一）
- 年度表記（「2026年度」か「FY2026」のどちらかに統一）
- %の小数桁、全角・半角（数字・英字は半角）
- 同じものの呼び方（「SFA」と「営業支援システム」の混在など）

### 要確認の警告
`save()` 実行時に「要確認」として、タイトルが2行を超える、本文があふれる可能性、強調の使いすぎ、などが出力される。**警告がなくなるまで直してから**出力すること（あふれ推定は概算なので、画像QAでも確認する）。

画像を確認し、文字のはみ出し・重なり・空白の偏りがないかを見る。QA環境ではメイリオの代わりに Noto Sans CJK で描画されるため、見た目は近似である点に注意。

## 手動でスライドを追加する場合

生成した.pptxには「CONTENT_手動追加用」レイアウトが入っている。PowerPointの「新しいスライド」からこのレイアウトを選ぶと、タイトル・セクション表示・本文・出典欄が同じ位置に配置される。ユーザーに聞かれたらこの方法を案内する。

## 個人・企業を特定できる情報の扱い

- 表紙の作成者、資料のメタデータ（作成者名）、サンプルや仮置きの文言に、実在の個人名・会社名・ブランド名を入れない。ユーザーが資料の中身として明示的に指定した場合のみ記載する
- 作成者や組織名が未指定の場合は「〇〇部」などの伏せ字にする
- `new Deck({ author })` には、ユーザーが指定した表記のみを入れる（未指定なら「〇〇部」）

## 出力時の報告

ファイルを提示したら、以下を簡潔に添える。
- 構成（何枚、どのセクション）
- 仮置きにした数値や、メモに不足していて補った・保留した点
- 縦読みチェックで直した点（あれば）
